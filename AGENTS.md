## Tone rules

Avoid generic student portfolio language.

Banned unless specifically justified:

- passionate developer
- tech enthusiast
- aspiring software engineer
- quick learner
- innovative solutions
- I love coding

Prefer:

- built
- automated
- validated
- debugged
- shipped
- mapped
- documented
- ranked
- measured
- proof trail
- case file
- workflow
- system
- validation

## Design direction

The portfolio should feel like:

- personal platform
- sci-fi editorial world
- systems-builder field record
- technical field journal
- ML/data lab archive
- materials archive
- serious case-file gallery
- premium cinematic interface
- quiet monumental desert-to-cosmos journey

It should not feel like:

- generic resume template
- neon hacker cliché
- random 3D showcase
- SaaS landing page clone
- cluttered project dump
- ML product marketing page
- unrelated image collage

## Project gallery rules

Main Project Gallery should include serious selected projects only:

- NameFrame
- PersonalCloud
- JEDI
- ClipHawk
- ML Atlas
- FIFA Predictor

Tiny builds, chaotic utilities, UI experiments, weekend apps, and mini repos belong in Tiny Builds Shelf, not Project Gallery.

## Work Console lanes

Work Console must show three vertical lanes:

1. ML + Data
2. Full-stack Products
3. Automation + Learning Systems

Each lane should show current work, outputs, examples, and proof artifacts.

## GitHub Map rules

GitHub Map should cluster repos into:

- ML Lab
- Full-Stack Systems
- Automation
- Learning Repos
- Tiny Builds
- Archived / Hidden

Do not display every repo as equally important.

## Animation rules

- One dominant animation idea per section.
- Hero may be cinematic.
- Other sections should be purposeful and restrained.
- Respect reduced motion.
- Mobile must stay smooth.
- Do not add random animation just because it is possible.

## MCP usage rules

Use MCPs only when they unlock a real workflow:

- GitHub MCP: inspect repos, READMEs, code, proof.
- Context7 MCP: check current framework/library docs.
- Playwright MCP: browser QA after implementation.
- Chrome DevTools MCP: performance/rendering/console checks.
- Figma MCP: only if a real Figma file/moodboard exists.

Do not use broad-access or random MCPs without user approval.

## Before coding

Before implementation, produce:

1. Narrative plan
2. Content/data plan
3. Visual language plan
4. Animation plan
5. Component breakdown
6. Missing proof list

Then implement section by section.

## Before finishing

Run available checks:

- lint
- typecheck
- build
- browser QA if available
- mobile review
- reduced-motion review

If something cannot be verified, say so explicitly.
